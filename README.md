# 1. گیت `merge` و `rebase`

## ۱. دستور `git merge`

دستور `git merge` برای ترکیب تغییرات دو شاخه (Branch) در گیت استفاده می‌شود.
تغییرات شاخه‌های مختلف را در یک شاخه‌ی واحد ترکیب می‌کند و ضمن حفظ تاریخچه، کار را یکپارچه می‌کند.

### نحوه ترکیب تغییرات

اگر شاخه `main` و شاخه `feature` پس از ایجاد یک کامیت مشترک، هرکدام کامیت‌های جدیدی داشته باشند، گیت معمولاً یک **Merge Commit** ایجاد می‌کند که دو والد دارد و تاریخچه دو شاخه را به هم متصل می‌کند.

اگر شاخه مقصد هیچ تغییر مستقلی نداشته باشد، ممکن است ادغام به‌صورت **Fast-forward** انجام شود. در این حالت، گیت فقط اشاره‌گر شاخه مقصد را جلو می‌برد و کامیت جدیدی ایجاد نمی‌کند.

### شکل تاریخچه کامیت‌ها

در حالت ایجاد Merge Commit، تاریخچه شاخه‌ها و نقطه ادغام آن‌ها حفظ می‌شود.

<img src=https://media.geeksforgeeks.org/wp-content/uploads/20230516192653/git-farwad-merging.png />

<img src=https://media.geeksforgeeks.org/wp-content/uploads/20230516192737/git-three-way-merging.png />


### موقعیت مناسب استفاده

**مثال:** زمانی که چند نفر روی شاخه‌های جداگانه یک پروژه کار می‌کنند و می‌خواهیم قابلیت جدیدی را به شاخه اصلی اضافه کنیم، بدون اینکه تاریخچه واقعی توسعه از بین برود.


**دلیل انتخاب:** استفاده از `merge` باعث حفظ تاریخچه شاخه‌ها و مشخص شدن زمان و نحوه ادغام تغییرات می‌شود. این ویژگی برای پروژه‌های تیمی و بررسی روند توسعه مناسب است.


## ۲. دستور `git rebase`

دستور `git rebase` برای انتقال کامیت‌های یک شاخه به نقطه شروع جدید استفاده می‌شود. این دستور کامیت‌های شاخه را بر اساس وضعیت جدید شاخه مقصد، مجدداً اعمال می‌کند.

### نحوه ترکیب تغییرات

برخلاف `merge`، دستور `rebase` معمولاً یک Merge Commit ایجاد نمی‌کند. در عوض، کامیت‌های شاخه موردنظر را به ترتیب روی پایه جدید بازسازی می‌کند.

از آنجا که این کامیت‌ها دوباره ایجاد می‌شوند، شناسه (Hash) آن‌ها معمولاً تغییر می‌کند؛ حتی اگر محتوای تغییرات یکسان باشد.

### شکل تاریخچه کامیت‌ها

پس از اجرای `rebase`، تاریخچه معمولاً خطی‌تر می‌شود و شاخه ویژگی به‌صورت ادامه‌ای از شاخه اصلی نمایش داده می‌شود.

<img src=https://media.geeksforgeeks.org/wp-content/uploads/20250305094419023965/Rebasing-in-git.png />


### موقعیت مناسب استفاده

**مثال:** زمانی که در حال توسعه یک قابلیت جدید هستیم و می‌خواهیم پیش از ادغام آن، تغییرات جدید شاخه `main` را دریافت کنیم و تاریخچه توسعه را خطی و خوانا نگه داریم.

**دلیل انتخاب:** استفاده از `rebase` باعث می‌شود کامیت‌های شاخه ویژگی پس از آخرین تغییرات شاخه اصلی قرار بگیرند و تاریخچه بدون Merge Commit اضافی، ساده‌تر و خواناتر شود.

#  2. انتخاب بخشی از تغییرات


## ۱. منظور از Hunk در خروجی Diff چیست؟

در Git، دستور `diff` برای نمایش تفاوت بین دو نسخه از یک فایل استفاده می‌شود. خروجی این دستور تغییرات را به بخش‌هایی تقسیم می‌کند که هر بخش از خطوط مرتبط با یکدیگر تشکیل شده است. به هر یک از این بخش‌ها **Hunk** گفته می‌شود.

هر Hunk معمولاً شامل خطوط اضافه‌شده، حذف‌شده و تعدادی خط از اطراف تغییرات است تا محل و مفهوم تغییر مشخص باشد.

## ۲. بررسی تعاملی تغییرات با خط فرمان

برای بررسی تغییرات فایل‌ها و انتخاب بخش‌هایی از آن‌ها جهت قرار گرفتن در ناحیه `staging`، می‌توان از دستور زیر استفاده کرد:

</div>

```bash
git add -p <file name>
```

<div dir="rtl">

این دستور تغییرات فایل‌ را به‌صورت تعاملی نمایش می‌دهد و اجازه می‌دهد مشخص کنیم کدام Hunkها برای کامیت بعدی انتخاب شوند.

<img src=https://miro.medium.com/v2/resize:fit:1400/format:webp/1*7dBrQ9Q_eh5dkV1GJBbrmQ.png />

پس از اجرای دستور، Git هر Hunk را نمایش می‌دهد و از ما می‌خواهد درباره اضافه کردن آن به ناحیه `staging` تصمیم بگیریم.

در حین اجرای دستور، گزینه‌های زیر در دسترس هستند:

| گزینه | عملکرد |
|---|---|
| `y` | اضافه کردن Hunk فعلی به ناحیه `staging` |
| `n` | رد کردن Hunk فعلی و بررسی بخش بعدی |
| `q` | خروج از حالت تعاملی |
| `a` | اضافه کردن Hunk فعلی و تمام Hunkهای باقی‌مانده همان فایل |
| `d` | رد کردن Hunk فعلی و تمام Hunkهای باقی‌مانده همان فایل |
| `s` | تقسیم Hunk فعلی به بخش‌های کوچک‌تر، در صورت امکان |
| `e` | ویرایش دستی Hunk برای انتخاب دقیق‌تر خطوط |
| `?` | نمایش راهنمای گزینه‌ها |

با وارد کردن `s` ما Hunk فعلی را به Hunk های کوچک تر تقسیم می کنیم.  و سپس باانتخاب کردن Hunk مورد نظر خود کامیت را انجام می دهیم.

<img src=https://miro.medium.com/v2/resize:fit:1400/format:webp/1*gOqt8JhFUX89KRO15O0EMg.png />

و سپس باقی Hunk ها را کامیت می کنیم.

# 3. یافتن منشأ خطا

## ۱. دستور `git bisect` چیست؟

دستور `git bisect` ابزاری در Git برای پیدا کردن کامیتی است که یک خطا (Bug) را وارد پروژه کرده است. این دستور با استفاده از روش **جست‌وجوی دودویی (Binary Search)**، تاریخچه کامیت‌ها را بررسی می‌کند و محدوده جست‌وجو را در هر مرحله کوچک‌تر می‌کند.

به‌جای بررسی تک‌تک کامیت‌ها، Git یک کامیت میانی را انتخاب می‌کند و از ما می‌خواهد مشخص کنیم که نسخه مربوط به آن سالم است یا معیوب.

## ۲. مراحل استفاده از `git bisect`

برای شروع، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git bisect start
```

<div dir="rtl">

این دستور فرایند جست‌وجو را آغاز می‌کند.


ابتدا کامیتی را مشخص می‌کنیم که در آن خطا وجود دارد. معمولاً این کامیت، آخرین نسخه معیوب پروژه است.

</div>

```bash
git bisect bad
```

<div dir="rtl">

سپس یک کامیت قدیمی‌تر را که مطمئن هستیم سالم بوده است، مشخص می‌کنیم. 

</div>

```bash
git bisect good <commit-hash>
```

<div dir="rtl">

با مشخص شدن این دو نقطه، Git می‌داند که خطا در محدوده کامیت‌های بین نسخه سالم و نسخه معیوب وارد شده است.

گیت یک کامیت میانی را انتخاب می‌کند و فایل‌های پروژه را به وضعیت همان کامیت تغییر می‌دهد. در این مرحله، باید پروژه را آزمایش کنیم تا مشخص شود خطا وجود دارد یا خیر.

اگر نسخه فعلی سالم باشد، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git bisect good
```

<div dir="rtl">

اگر نسخه فعلی همچنان دارای خطا باشد، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git bisect bad
```

<div dir="rtl">

گیت بر اساس پاسخ ما، محدوده جست‌وجو را کوچک‌تر می‌کند و کامیت بعدی را برای بررسی انتخاب می‌کند. این فرایند تا مشخص شدن کامیت معرفی‌کننده خطا ادامه می‌یابد.

وقتی جست‌وجو تمام شود، Git کامیتی را معرفی می‌کند که به‌عنوان نخستین کامیت معیوب در محدوده بررسی‌شده شناسایی شده است. این همان کامیتی است که وضعیت پروژه را از سالم به معیوب تغییر داده است.

پس از پایان بررسی، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git bisect reset
```

<div dir="rtl">


## ۳. مثال عملی

فرض کنید در یک پروژه، برنامه تا کامیت `A` بدون مشکل اجرا می‌شده، اما در کامیت `H` خطایی مشاهده کرده‌ایم. در این فاصله چندین کامیت ثبت شده‌اند و نمی‌دانیم کدام‌یک باعث بروز خطا شده است.

تاریخچه اولیه به شکل زیر است:

</div>

```text
A---B---C---D---E---F---G---H
^                           ^
سالم                        معیوب
```

<div dir="rtl">

برای پیدا کردن منشأ خطا، ابتدا فرایند را آغاز می‌کنیم و کامیت‌های سالم و معیوب را مشخص می‌کنیم.

</div>

```bash
git bisect start
git bisect bad H
git bisect good A
```

<div dir="rtl">

Git ممکن است کامیت `E` را برای بررسی انتخاب کند. فرض کنیم با اجرای برنامه متوجه شویم که این نسخه سالم است:

</div>

```bash
git bisect good
```

<div dir="rtl">

در نتیجه، Git فقط نیمه معیوب باقی‌مانده را بررسی می‌کند. فرض کنیم کامیت بعدی انتخاب‌شده `G` باشد و آزمایش نشان دهد که خطا در آن وجود دارد:

</div>

```bash
git bisect bad
```

<div dir="rtl">

سپس Git محدوده را کوچک‌تر می‌کند و ممکن است کامیت `F` را انتخاب کند. اگر آزمایش نشان دهد که این نسخه معیوب است، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git bisect bad
```

<div dir="rtl">

در این مثال، Git می‌تواند کامیت `F` را به‌عنوان نخستین کامیت معیوب شناسایی کند؛ زیرا کامیت قبلی یعنی `E` سالم بوده است.

# 4. بررسی تغییرات پیش از کامیت

## سؤال ۱:

برای بررسی وضعیت مخزن و مشاهده تغییرات فایل‌ها، از دستورهای زیر استفاده می‌کنیم:

</div>

```bash
git status
git diff
git diff --staged
```

<div dir="rtl">

**توضیح دستورها:**

- `git status`: وضعیت فایل‌ها را نشان می‌دهد؛ از جمله تغییرات واردشده به ناحیه `staging`، تغییرات واردنشده به این ناحیه و فایل‌های `untracked`.
- `git diff`: تغییرات فایل‌های `tracked` را که هنوز وارد ناحیه `staging` نشده‌اند، نمایش می‌دهد.
- `git diff --staged`: تغییراتی را نمایش می‌دهد که وارد ناحیه `staging` شده‌اند و برای کامیت بعدی آماده هستند.

**تفاوت تغییرات Staged و Unstaged:**

- **Staged Changes:** تغییراتی هستند که با دستور `git add` به ناحیه `staging` منتقل شده‌اند و در صورت اجرای کامیت معمولی، ثبت خواهند شد.
- **Unstaged Changes:** تغییرات جدیدی هستند که پس از آخرین اجرای `git add` در فایل ایجاد شده‌اند و هنوز وارد ناحیه `staging` نشده‌اند.

## سؤال ۲:

فقط تغییراتی که پیش از اجرای کامیت در ناحیه `staging` قرار گرفته‌اند، ثبت می‌شوند.

**دلیل:** دستور `git commit` در حالت معمول، محتوای ناحیه `staging` را ثبت می‌کند، نه تمام تغییرات موجود در فایل‌های کاری. به همین دلیل، تغییرات `unstaged` در کامیت فعلی قرار نمی‌گیرند.

 

## سؤال ۳:

برای جلوگیری از نمایش و اضافه شدن فایل‌های موقت و `untracked` پوشه `/tmp` به کامیت‌های آینده، می‌توانیم این مسیر را در فایل `.gitignore` قرار دهیم.


**آیا `.gitignore` برای فایل‌های قبلاً Tracked کافی است؟**

خیر. فایل `.gitignore` به‌طور معمول فقط از ردیابی شدن فایل‌های جدید و `untracked` جلوگیری می‌کند. اگر فایلی قبلاً `tracked` شده باشد، اضافه کردن نام آن به `.gitignore` باعث توقف ردیابی آن نمی‌شود.

برای مثال، اگر پوشه‌ای به نام `tmp` قبلاً در مخزن ردیابی شده باشد، ابتدا باید آن را از ناحیه ردیابی Git خارج کنیم، بدون اینکه فایل‌های محلی حذف شوند:

</div>

```bash
git rm -r --cached tmp/
```

<div dir="rtl">

گزینه `--cached` باعث می‌شود فایل‌ها از فهرست فایل‌های تحت ردیابی Git خارج شوند، اما نسخه‌های موجود آن‌ها در پوشه کاری باقی بمانند.



سپس تغییرات مربوط به `.gitignore` و حذف از ناحیه ردیابی را کامیت می‌کنیم:

</div>

```bash
git add .gitignore
git commit -m "Ignore temporary files"
```

# 5. رفع 'merge conflict' در کار گروهی

## سوال ۱:

هنگام ادغام شاخه `description-feature` در `main`، گیت نمی‌تواند به‌طور خودکار تشخیص دهد که کدام‌یک از دو تغییر باید حفظ شود؛ بنابراین، یک **Merge Conflict** رخ می‌دهد.

این تعارض به این دلیل ایجاد می‌شود که هر دو شاخه، یک بخش مشترک از فایل را به شکل متفاوتی تغییر داده‌اند و Git نمی‌تواند بدون تصمیم‌گیری درباره محتوای نهایی، آن‌ها را با اطمینان ادغام کند.

**آیا هر تغییری در یک فایل الزاماً باعث Conflict می‌شود؟**

خیر. اگر دو نفر بخش‌های متفاوتی از یک فایل را تغییر دهند، Git معمولاً می‌تواند تغییرات را به‌صورت خودکار ادغام کند.

## سوال ۲:

پس از گزارش تعارض هنگام ادغام، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git status
```

<div dir="rtl">

این دستور فایل‌هایی را که دارای تعارض هستند، معمولاً با عنوان `both modified`، مشخص می‌کند.

برای مشاهده فایل‌هایی که هنوز تعارض حل‌نشده دارند، می‌توانیم از دستور زیر استفاده کنیم:

</div>

```bash
git diff --name-only --diff-filter=U
```

<div dir="rtl">

این دستور نام فایل‌های دارای تعارض حل‌نشده را نمایش می‌دهد.

با باز کردن فایل `README.md`، ممکن است بخش متعارض را به شکل زیر مشاهده کنیم:

</div>

```text
<<<<<<< HEAD
متن تغییر یافته در شاخه main
=======
متن تغییر یافته در شاخه description-feature
>>>>>>> description-feature
```

<div dir="rtl">

این علامت‌ها را **Conflict Markers** می‌نامند و هرکدام نقش مشخصی دارند.

این علامت‌ها به‌صورت خودکار در فایل قرار می‌گیرند تا دو نسخه متعارض از یک بخش را نشان دهند. آن‌ها بخشی از محتوای نهایی موردنظر نیستند و باید هنگام حل تعارض حذف شوند.

## سوال ۳:

فرض می‌کنیم اطلاعات هر دو تغییر باید حفظ شوند. 

فایل `README.md` را در ویرایشگر باز می‌کنیم و بخش متعارض را به شکلی تغییر می‌دهیم که هر دو اطلاعات موردنیاز حفظ شوند.

پس از ویرایش فایل، می‌توانیم بررسی کنیم که هیچ علامت تعارضی در متن باقی نمانده باشد.

</div>

```bash
git diff --check
git diff
```

<div dir="rtl">

دستور `git diff --check` خطاهای مربوط به فاصله‌های انتهایی و برخی مشکلات قالب‌بندی را گزارش می‌کند، اما به‌تنهایی تضمین نمی‌کند که تمام Conflict Markers حذف شده‌اند.

برای اطمینان از اینکه علامت ها در فایل وجود ندارند میتوانیم از دستور زیر استفاده کنیم:

</div>

```bash
grep -n -E '^(<<<<<<< |=======|>>>>>>> )' README.md
```

<div dir="rtl">

اگر خروجی نداشته باشد، این الگوها در ابتدای خطوط فایل پیدا نشده‌اند. 

پس از حل تعارض و بررسی فایل، آن را به ناحیه `staging` اضافه می‌کنیم:

</div>

```bash
git add README.md
```

<div dir="rtl">

با این دستور، Git متوجه می‌شود که تعارض این فایل را حل کرده‌ایم و نسخه فعلی آن را برای ثبت آماده کرده‌ایم.

برای اطمینان از اینکه تعارض حل شده و فایل در ناحیه `staging` قرار گرفته است، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git status
```

<div dir="rtl">

در این مرحله، نباید فایل `README.md` در بخش فایل‌های دارای تعارض حل‌نشده نمایش داده شود.

پس از حل تمام تعارض‌ها، ادغام را با دستور زیر تکمیل می‌کنیم:

</div>

```bash
git commit
```

<div dir="rtl">

اگر Git پیام پیش‌فرض کامیت ادغام را باز کند، می‌توانیم آن را تأیید کنیم. در بعضی شرایط نیز می‌توانیم از دستور زیر استفاده کنیم:

</div>

```bash
git merge --continue
```

<div dir="rtl">

پس از تکمیل ادغام، برای بررسی نتیجه می‌توانیم از دستورهای زیر استفاده کنیم:

</div>

```bash
git status
git log --oneline --graph --all
```

<div dir="rtl">

دستور اول وضعیت مخزن را نشان می‌دهد و دستور دوم تاریخچه کامیت‌ها و نحوه اتصال شاخه‌ها را نمایش می‌دهد.

## سوال ۴:

می‌توانیم از دستور زیر استفاده کنیم:

</div>

```bash
git merge --abort
```

<div dir="rtl">

این دستور تلاش می‌کند عملیات ادغام نیمه‌تمام را لغو کند و شاخه و وضعیت کاری را به حالت پیش از شروع Merge بازگرداند.

# 6. انتخاب روش مناسب برای بازگرداندن تغییرات

## سوال ۱:

### دستور مناسب

</div>

```bash
git restore notes.txt
```

<div dir="rtl">

### اثر دستور

- **Working Tree:** تغییرات ثبت‌نشده فایل `notes.txt` حذف می‌شوند و محتوای آن به نسخه موجود در ناحیه `staging` بازمی‌گردد.
- **Staging Area:** تغییری نمی‌کند؛ چون نسخه موجود در این ناحیه با آخرین کامیت یکسان است.
- **Commit History:** هیچ تغییری نمی‌کند.

## سوال ۲:

### دستور مناسب

</div>

```bash
git restore --staged notes.txt
```

<div dir="rtl">

### اثر دستور

- **Working Tree:** تغییرات فایل حفظ می‌شوند.
- **Staging Area:** تغییرات فایل از ناحیه `staging` خارج می‌شوند.
- **Commit History:** هیچ تغییری نمی‌کند.

## سوال ۳:

### دستور مناسب:

ابتدا شناسه کامیت اشتباه را پیدا می‌کنیم:

</div>

```bash
git log --oneline
```

<div dir="rtl">

سپس با استفاده از شناسه کامیت موردنظر، دستور زیر را اجرا می‌کنیم:

</div>

```bash
git revert <commit-hash>
```

<div dir="rtl">


Git یک کامیت جدید ایجاد می‌کند که تغییرات کامیت اشتباه را معکوس می‌کند. در نتیجه، اثر آن کامیت در نسخه فعلی پروژه برگردانده می‌شود، اما خود کامیت قبلی در تاریخچه باقی می‌ماند.

پس از بررسی نتیجه، کامیت بازگردانی را `Push` می‌کنیم:

</div>

```bash
git push origin main
```

<div dir="rtl">

### اثر دستور

- **Working Tree:** پس از تکمیل موفقیت‌آمیز عملیات، فایل‌ها تغییر می‌کنند تا اثر کامیت هدف معکوس شود.
- **Staging Area:** در فرایند عادی `git revert`، تغییرات معکوس‌شده برای ثبت آماده می‌شوند و با ایجاد کامیت جدید ثبت خواهند شد.
- **Commit History:** کامیت اشتباه حذف نمی‌شود؛ یک کامیت جدید برای معکوس کردن اثر آن به تاریخچه اضافه می‌شود.

### چرا `git reset` و `push --force` مناسب نیستند؟

به دلیل اینکه هم تیمی ها  آن کامیت را دریافت کرده اند ممکن است با حذف کردن کامیت  متوجه اشتباه بودن آن کامیت نشوند و دوباره نیاز به هماهنگ سازی  داشته باشند و یا هنگام ادغام با مشکل مواجه شوند.

در مقابل، `git revert` تاریخچه مشترک را حفظ می‌کند و یک کامیت جدید برای اصلاح ایجاد می‌کند. به همین دلیل، برای بازگرداندن اثر یک کامیت منتشرشده روی شاخه مشترک، معمولاً انتخاب مناسب‌تری است.
